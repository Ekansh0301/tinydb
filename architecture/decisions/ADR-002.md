# ADR-002: A deterministic orchestrator as a state machine, with bounded back-edges

- **Date:** 2026-11-16
- **Status:** Accepted
- **Decision area:** D2 Control flow

## Context
The assignment fixes six stages, gates between them, and the allowed back-edges: a test failure goes to stage 3 and, if it persists, to stage 2; review problems go to the stage that needs fixing, at most twice. Someone has to decide when to go back. If an agent decided, a faulty agent could bypass a gate or loop on a budget we cannot afford.

## Decision
A Python orchestrator (`workflow/autose/orchestrator.py`) is a state machine with the states `S1..S6`, `DONE` and `STOPPED`. The rules are code:

- A stage moves forward only when its gate passes (ADR-007).
- Tests fail: `S4 -> S3`, at most 2 retries. The same acceptance criterion fails in two attempts: `S4 -> S2` (changed to `S4 -> S1` by the second amendment below).
- Reviewer verdict `REQUEST_CHANGES` with issue class `approach`: `S6 -> S2`; class `code`: `S6 -> S3`. At most 2 review rounds in total.
- Any exhausted budget: `STOPPED`, with the reason written into the stage's artifact.

Agents choose what to write or edit inside a stage; they never choose the next stage. The reviewer picks the issue class as part of its verdict, but the orchestrator acts on it.

Across Actions jobs the control flow is a chain of jobs (`gate -> build -> ci -> review -> next`). When a review needs more work, the `next` job starts a new workflow run with `round+1` and `from_stage` as inputs (`workflow_dispatch`, which the default token may call).

## Alternatives considered
- **Orchestrator agent that plans dynamically.** More adaptive, but its decisions cost tokens, vary between runs and are hard to audit. Rejected.
- **One long job with loops inside.** The simplest option, but one job would then hold the push right and the review right together, which breaks reviewer independence (ADR-008). Rejected.
- **Jobs that trigger each other through events.** Events created by the default token do not start other workflows, so this fails silently. Rejected.

## Consequences
- The state machine keeps every run on its designed path, with each stage doing only its own job, and errors become visible: every attempt of every stage is recorded in `stages.jsonl`.
- Real runs changed it twice (the amendments below). A criterion that fails twice now goes back to requirements, because a repeated failure can come from a criterion that asks for something the code cannot provide; and tests that cannot even be collected are blamed on the tester, not on the implementer.
- A back-edge to stage 2 re-runs planning with the failure evidence attached (ADR-003), which costs tokens; the budget in ADR-009 caps this.
- The orchestrator cannot recover from a failure type its rules do not cover. It stops and says so.

## Amendment (2026-11-16, before the first run on GitHub)
- "At most 2 review rounds" is implemented as at most **two fix cycles**: feedback can go back twice, so a run can contain up to three reviews (`MAX_FIX_CYCLES = 2` in `workflow/autose/config.py`). This is our reading of "requested changes go back to the stage that needs fixing, at most twice".
- Stage attempts per round: spec 3, design 3, implementation 3 in total, tester 3, return to design 1. These limits are in `workflow/autose/orchestrator.py`.

## Second amendment (2026-11-17)
When the same acceptance criterion fails twice in stage 4, the run goes back to **stage 1** (requirements), not stage 2, once per round. Replays of stage 4 showed that a repeated failure can come from a criterion that asks for something the code does not offer (an invented parameter), which a new design cannot fix. Stage 2 runs again afterwards in any case, so a design problem is also corrected.
