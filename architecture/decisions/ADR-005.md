# ADR-005: Tools are in-process functions, a different small set per role

- **Date:** 2026-11-16
- **Status:** Accepted
- **Decision area:** D5 Tools

## Context
Agents need to read code, edit it and run tests, and nothing else. Every tool definition costs tokens in every request, and our request limit is about 7,000 tokens. Agents run code on a runner that also holds API secrets, so what a tool can reach matters more than how convenient it is.

## Decision
Tools are Python functions in `workflow/autose/tools.py`, exposed to the model through the chat API's function-calling interface. No MCP server and no `gh` CLI is given to any agent. The orchestrator, not an agent, uses the `gh` CLI and git for everything on GitHub (push, pull request, comments).

| Role | Tools | Limits |
|---|---|---|
| Planner | `open_file`, `list_dir`, `search` | read only |
| Implementer | the above plus `edit_file`, `write_file`, `run` | cannot write `tests/test_autose_*`; cannot overwrite existing files with `write_file` |
| Tester | read tools plus `write_file`, `edit_file`, `run` | may write or edit only `tests/test_autose_<name>.py` |
| Reviewer | read tools plus `run` | cannot write anything |

All paths are resolved inside the work directory. `experiment/`, `architecture/`, `workflow/`, `results/`, `.github/` and `.git` are refused for reading and writing, so an agent cannot read the hidden tests, the workflow prompts or its own gates. `run` accepts only `python -m pytest`, `python -m compileall` and `python -c`, is started without a shell, and gets an empty environment (no API keys, a temporary home and `TMPDIR`); when bubblewrap works on the machine it also runs without network and with a read-only filesystem. Tool output is cut at 2,600 characters (first plan 3,500; ADR-011, `config.py`).

Tool names follow what the model expects. In the first runs `gpt-oss-120b` repeatedly called tools named `open_file` and `search` that we had not offered (we had `read_file` and `grep`); every such call was rejected by the API and wasted a request. We renamed the tools and keep aliases for the common argument spellings (`file`, `start_line`, `regex`).

## Alternatives considered
- **MCP servers (filesystem, GitHub).** Standard, but each adds startup time and a large tool list, and the GitHub server would give agents write access we do not want. Rejected.
- **Give agents the `gh` CLI.** Flexible, but an agent could then push, comment or close issues. Rejected; the orchestrator does that after a gate passes.
- **Free shell access in a container.** Most capable. Rejected: more failure modes and more risk for little gain on a library this size.

## Consequences
- Each role can only do what its stage needs; a prompt-injected agent cannot push, merge or read secrets.
- The tool layer is code we can unit-test (`workflow/tests/test_tools.py` checks the path rules, role limits and that commands never see API keys).
- Agents cannot run arbitrary shell commands, so a task that needs one (installing a package) is out of reach by design.
