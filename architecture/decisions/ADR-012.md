# ADR-012: Models by role, final assignment

- **Date:** 2026-11-18
- **Status:** Accepted
- **Supersedes:** ADR-006 (kept unchanged, with its five amendments, as the history of how the choice was made)
- **Decision area:** D6 Models

## Context
ADR-006 chose models from probes run on a laptop and was then revised five times because the real workflow, on the GitHub runner, contradicted the probes: Groq's daily token quota (200,000 tokens per key and day), a NVIDIA endpoint that hung only inside the pipeline, a model that cut off its own tool arguments, and models that looped on exploration. The amendments contradict one another, so the current assignment is stated once here.

## Decision
| Role | Model | Evidence that it completes its stage on the runner |
|---|---|---|
| Planner (stages 1, 2) | `openai/gpt-oss-120b` (Groq) | stages 1 and 2 passed in the complete run 44158195212 |
| Implementer (stage 3) | `openai/gpt-oss-120b` (Groq) | stage 3 passed in the same run, and in four earlier runs |
| Tester (stage 4) | `openai/gpt-oss-20b` (Groq) | complete test files in 3 of 3 replays and stage 4 passed in run 44158195212; Laguna and Qwen failed in three runs |
| Reviewer (stage 6) | `nemotron-3.5-super-vl-120b`, then `nemotron-3-ultra-550b`, then `qwen3.8-27b` | valid, evidence-backed reviews on the seeded pull requests and on PR #34 |
| Injection screen | `llama-prompt-guard-2-86m` (Groq) | scores 0.998 on an injected issue and 0.0004 on a normal one |

Rules that come from the amendments:
1. **A model is chosen only after it has completed its stage inside the workflow on the runner.** A laptop probe of a few requests is not evidence.
2. **Builder roles are pinned**: one model each, no fallback to another vendor, so every result is attributable. A builder whose model is unavailable stops the run with that reason.
3. **The reviewer has a chain** because an unavailable reviewer must neither block nor approve silently; the tier that answered is recorded. A review that is invalid (no JSON, no evidence, budget used up) is retried once on the next tier; if the second attempt is invalid too, there is no review and therefore no approval.
4. **The reviewer is a different vendor from every builder.** The tester is a smaller model of the implementer's family: a different-family tester (Qwen) was tried and was less reliable.
5. **Quota is part of the design**: one pipeline run uses about 115,000 `gpt-oss-120b` tokens (planner and implementer), the tester and the reviewer use other quotas, and six keys allow about 1.2 million per day. The number of recorded runs is planned from that figure (`experiment/protocol.md`).

## Alternatives considered
- **Cross-vendor fallback for builders** (tried, ADR-006 second amendment): hides which model produced a result. Rejected.
- **A stronger or larger tester or planner** (Nemotron Ultra, Laguna, Qwen): Laguna hung or timed out and Qwen truncated its output on the runner. Nemotron Ultra answered reliably but would put a builder in the reviewer's vendor.
- **Gemini** as reviewer: it answered none of our requests during the probe.

## Consequences
- The configuration in `workflow/autose/config.py` and this table must agree; a unit test checks that builders are pinned and the tester differs from the implementer.
- A change of model after the freeze needs a new ADR and repeats the affected runs.
- Threats to validity: all builders are one family; the reviewer's first two tiers share a vendor; results hold for small free models only.
