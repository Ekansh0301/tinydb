# ADR-008: Reviewer independence by separate job, model, prompt, inputs and permissions

- **Date:** 2026-11-16
- **Status:** Accepted, tested (experiments E2 and E2b; one change made, see the result below)
- **Decision area:** D8 Reviewer independence

## Context
Reviewers who have information about the builder's context tend to approve. The opposite can also happen: in a quick check, `gpt-oss-120b` rejected even a harmless diff, so a model can fail in the other direction as well (reject everything). Independence therefore has to be built into the structure, and then measured.

## Decision
We ensured independence at five levels.
1. **Own job.** The reviewer runs in a job that is separate from `build`. It does not share a process, a filesystem or an environment with the agents.
2. **Own model and vendor.** NVIDIA Nemotron models first, Qwen on Groq as the last tier (ADR-006). No builder model reviews builder output.
3. **Own prompt.** The system prompt tells it to look for defects first, to prove claims by running code, and to treat the author as unknown.
4. **Own inputs.** The issue text, `diff.patch` and the repository at the pull-request head commit. Not `spec.md`, `design.md`, `test_report.md` or any conversation (ADR-003).
5. **Own permissions.** `contents: read` only: no push, no merge, no workflow dispatch. It writes `review.json` and `review.md` as a workflow artifact and the later `next` job posts the comment (see the amendment below). Its tools are read, grep, run tests and run Python, and commands run with an empty environment, so no API key is visible to code it executes.

**Against rubber-stamping.** The reviewer returns structured JSON: `verdict`, `issue_class` (`approach` or `code`), and a list of checks, each with a file and line or a command output as evidence. A verdict is valid only if it has at least two checks with evidence and the reviewer ran a command. An invalid review is retried once on the next tier; a second invalid review means no review. A review that comes back as general comments, or that runs out of budget, counts as no review and never as approval. The five seeded pull requests (known wrong and known good, labels hidden from the reviewer) serve as a calibration set, and the false-approval and false-rejection rates are reported.

## Alternatives considered
- **Same model, fresh context.** Cheap, and it removes the shared conversation but not the shared blind spots. Kept as the variant `same-model` in E2.
- **LLM judge that scores the diff only, with no code access.** It cannot test behaviour. Rejected.
- **Two reviewers voting.** Better coverage, but it doubles the cost on a tight budget. Rejected for now.
- **Human review only.** Required at the end, but it is not a substitute for the automated stage.

## Consequences
- The reviewer cannot be steered by the implementer's explanation. The downside is that it sees neither the specification nor the design, so it judges the change on the issue text alone and can miss defects that only the specification would reveal.
- Calibration costs five extra reviews per configuration.
- E2 compares `same-model` against this design on the seeded pull requests, by catch rate and false approvals. A result that shows no difference is also a valid result and would lead to a superseding ADR.

## Amendment (2026-11-16, before the first run on GitHub)
The reviewer job holds only `contents: read`. It does not post its own comment. It writes `review.json` and `review.md` as a workflow artifact; the later `next` job, which runs fixed code from `main`, posts the review on the pull request and records it on the runs branch. The reviewer runs code from a separate checkout of `main`, so a change inside the pull request cannot alter the reviewer or its prompt.

## Result of experiments E2 and E2b, and a change (2026-11-20)
Final reviewer code, three reviews of each of the five seeded pull requests per variant (`results/seeded.csv`, three correct and three defective pull requests as labelled in `experiment/seeded_prs/labels.csv`):

| Variant | Reviews | Valid | Wrong PRs caught | Correct PRs approved | Mean tokens |
|---|---|---|---|---|---|
| independent (Nemotron 3.5 Super first) | 15 | 14 | 8 of 9 | 6 of 6 | 54,000 |
| same-model (`gpt-oss-120b`, fresh context) | 15 | 14 | 1 of 9 | 5 of 6 | 3,400 |
| ultra-first (Nemotron 3 Ultra first, E2b) | 15 | 15 | 9 of 9 | 6 of 6 | 105,000 |

The same-model reviewer approved eight of nine defective pull requests: it ran the test suite once, read the pull request's own tests and approved. Our evidence rule did not prevent it: it checks that evidence is present, not that it could have found a defect. The independent reviewers ran their own snippets and found the cache and hash defects. The decision stands.

**Change.** The larger model (550B total, 55B active) gave no invalid review and caught every defect, at about twice the tokens. After the recorded pipeline runs the reviewer chain was changed to start with it (`autose-v1.2`; ADR-012 table updated). The recorded pipeline reviews were produced with the smaller model first, as frozen; the evidence for the change is the calibration, not a rerun of the pipeline.
