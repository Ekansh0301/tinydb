# ADR-009: Hard budgets, bounded loops, and untrusted-input handling

- **Date:** 2026-11-16
- **Status:** Accepted
- **Decision area:** D9 Safety and failures

## Context
Limits that matter here: 8,000 tokens per minute per key and about 7,000 per request on Groq; Actions jobs stop after their `timeout-minutes` (6 hours by default); an issue is text written by anyone, so it can carry instructions aimed at the agents; and the code agents write is executed on a runner that also holds API secrets.

## Decision
**Budgets (all configurable in one file, defaults below).**
- Per request: input truncated to 6,000 tokens; tool outputs capped at 4,000 characters.
- Per stage: at most 25 model calls and 60,000 tokens; a stage that exceeds either stops with its reason written to the artifact.
- Per run: at most 400,000 tokens and 2 review rounds. Totals are written to `state.json` and reported.
- Wall-clock: each job has `timeout-minutes` (build 40, review 20), each model call 90 s.
- Rate limits: key rotation on 429, exponential backoff with jitter, at most 5 retries, then the stage stops.
- Stuck stage detection: the same tool call with the same arguments three times in a row stops the stage.

**Untrusted input.**
- Issue and comment text reaches agents only inside a clearly delimited block marked as data, with an instruction not to follow directions found in it. It is truncated to 4,000 characters.
- The gate job scores the text with a prompt-injection classifier (ADR-006). A score above 0.9 stops the run and posts a comment asking a maintainer to review the text.
- Agents have no network tool and no secrets. API keys exist only in the orchestrator and reviewer processes; every shell command an agent runs gets an empty environment.
- Workflows never use `pull_request_target` and never check out code from an untrusted fork. The workflow refuses to run unless the repository is `Ekansh0301/tinydb`, so it cannot push anywhere else.
- Jobs get the minimum `permissions`. Nothing in the workflow can merge.

## Alternatives considered
- **Rely on the model to ignore injected text.** Weak and unmeasurable. Used as one layer only.
- **No classifier, only delimiters.** Cheaper, but gives no signal for the report. Classifier kept because it costs a single small request.
- **Run agent code in a container with no network.** Stronger, and Actions runners can do it, but it adds setup time and failure modes. Considered for later if a run shows the need.

## Consequences
- A legitimate, unusual issue may be stopped by the classifier (false positive); a maintainer re-triggers after review.
- Budgets can stop a run that would have succeeded with more effort. The stop reason is recorded so this is visible in results.
- We will test the gate with injection attempts in the five issues' variants and report what passed through.

## Amendment (2026-11-20): the values in force
The numbers above were the first plan; the code (`workflow/autose/config.py`, `workflow/autose/orchestrator.py`) uses these, changed after runs and recorded here:
- Request: prompt kept near 4,500 estimated tokens (5,500 to 6,000 for the design, implementation, testing and review stages), completion cap 1,100 to 2,000 tokens, tool output cut at 2,600 characters. The Groq limit of 8,000 tokens per minute and key is respected by a per-key window in the client.
- Stage: at most 25 model calls (24 for the reviewer) and 120,000 tokens (150,000 for the reviewer); the single-agent variant 70 calls and 300,000 tokens.
- Run: 400,000 tokens, checked before each stage; a spent budget stops the run at once. Review feedback goes back at most twice (two fix cycles, so up to three reviews, ADR-002).
- Time: model call 60 s (Groq) or 45 s (NVIDIA), four timeouts end a tier; jobs: build 90 minutes, review 30, next 10, gate 10.
- A bug in a stage or gate ends the run as a recorded stop (`internal error in <stage>`), never as a dead job (ADR-007 amendment).

## Amendment (2026-11-20): the injection screen was failing open, and what it catches
Testing the classifier on injected issue texts (`experiment/injection_test.py`) showed that it had not been working in the recorded runs. The rate-limit clamp added on 2026-11-16 refused every request whose prompt left less than 400 tokens of answer room, and the classifier asks for 5 tokens, so every call raised `TooLarge`. The gate caught the exception and used the score 0.0, so **the screen passed every issue**. The five issues are our own and benign (scored after the fix: 0.000 to 0.001), so no recorded result is affected, but the claim of this ADR was not true in practice.

Fix (`autose-v1.3`): a short answer is no longer refused as too large (`test_a_short_answer_request_is_not_refused_as_too_large`), and the gate **fails closed**: if the classifier cannot score any part of the text, the issue is not passed to the agents and a comment says so (`test_the_injection_screen_fails_closed`).

What the working screen catches (threshold 0.9): an instruction appended to a normal issue (0.993) and an instruction in the title (0.993) are blocked. A polite request addressed to the assistant (0.001), an instruction inside a code block (0.018) and a role override (0.004) are **not** blocked. The screen is therefore one layer. The others do not depend on the classifier: the text reaches agents only inside a delimited data block; agents have no network, no push or comment tool and no secrets (commands run with an empty environment); paths outside the source tree are refused; the workflow only pushes branches of this fork and cannot merge. An end-to-end run with an injected issue that the screen passes is in `experiment/injection_test.md`.
