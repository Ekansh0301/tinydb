# ADR-010: Triggers, who may start a run, and concurrent runs

- **Date:** 2026-11-16
- **Status:** Accepted
- **Decision area:** D10 Triggers

## Context
The assignment names two triggers: a label on an issue and a `/autose` comment. Anyone can comment on a public repository, and a run spends limited tokens and can push branches. Two triggers for the same issue can also arrive close together (a label added, then a comment).

## Decision
- **Events:** `issues: labeled` with the label `autose`; `issue_comment: created` where the comment body, trimmed, equals `/autose` and the comment is on an issue. The same comment on a pull request opened by this workflow asks for a fresh review of that PR (stage 6 only). A `workflow_dispatch` entry point exists for the `next` job to start a later round (see the amendments for how it was used).
- **Who:** the gate job checks the sender's repository permission through the API and requires `write` or higher. The association labels in the event payload are not trusted on their own. Everyone else gets no run and no comment.
- **Concurrency:** `concurrency: { group: autose-issue-<N>, cancel-in-progress: false }`. Runs for one issue queue up. The first step of the gate reads `state.json`; if a run for the issue is already active, the new trigger exits with a one-line comment. A finished or stopped issue can be started again only by a new explicit trigger.
- **Issues are never closed or edited by the workflow.** It only comments.

## Alternatives considered
- **Trigger on every new issue.** It wastes budget and exposes the agents to all input. Rejected.
- **`cancel-in-progress: true`.** It would kill a run halfway through a push and leave a half-written branch. Rejected.
- **Trust `author_association`.** Quick, but it describes the comment author, not the sender of a label event. We query the permission instead.

## Consequences
- Only maintainers can spend tokens. This is a small, explicit trust boundary.
- A duplicate trigger is visible as a short comment, which keeps the behaviour explainable.
- Comments that are not exactly `/autose` do nothing, so ordinary discussion cannot start runs.

## Amendment (2026-11-17, after Actions run 44162669429)
The first review that asked for changes (run 44162266775) made the `next` job start round 2 with `workflow_dispatch`, but the new run stopped at the gate: the sender was `github-actions[bot]`, which has no repository permission, so the permission check refused it. The gate now trusts a `workflow_dispatch` event whose sender is `github-actions[bot]` (the workflow's own token). That is safe because GitHub lets only a user with write access or a workflow of this repository create such an event; a comment or a label event from the bot is still checked (`test_only_the_workflows_own_token_is_trusted_for_dispatch`).

## Amendment (2026-11-20): how the triggers were used
A comment `/autose` on a pull request opened by the workflow asks for a fresh review of that pull request in the same round; it does not count as a further fix cycle (the first version of this ADR said it would). The label and issue-comment triggers were used on issue #7; the later recorded runs were started with `workflow_dispatch` through `experiment/drive.py`, which runs the same jobs behind the same gate. The gate's permission check applies to the label sender and the comment author; for a dispatch it applies to the sender, and the workflow's own token is trusted for the next round (first amendment).
