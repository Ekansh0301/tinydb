# ADR-006: Models by role, chosen from measured availability

- **Date:** 2026-11-16
- **Status:** Accepted, to be revisited after the first full runs
- **Decision area:** D6 Models

## Context
We have free access only: Groq (`gpt-oss-120b`, `gpt-oss-20b`, `qwen/qwen3.8-27b`, prompt-guard models) and NVIDIA's free endpoint, plus a Gemini key. Free endpoints differ in limits and availability. We probed them before choosing; results are in `experiment/model_probe.md`. Key findings: Groq allows 8,000 tokens per minute per key and rejects a larger single request; `gpt-oss-120b` made 8/8 tool calls at about 0.7 s; `qwen3.8-27b` made 6/8 (over-capacity errors); Gemini answered 0 requests; of ten NVIDIA models only `nemotron-3.5-super-vl-120b`, `nemotron-3-ultra-550b` and `laguna-xs-2.1` made 4/4 tool calls, and the two Nemotron models separated a correct from a subtly wrong diff 6/6 in a small smoke test.

## Decision
| Role | Model | Why |
|---|---|---|
| Planner, Implementer, Tester | `openai/gpt-oss-120b` (Groq, 5 keys rotated) | Most reliable tool use of the Groq models; fast; cost is zero. |
| Reviewer, tier 1 | `nvidia/nemotron-3.5-super-vl-120b-a12b` | Different vendor and family from the builder; reliable in the probe; accepts long context, so it can read whole files. |
| Reviewer, tier 2 | `nvidia/nemotron-3-ultra-550b-a55b` | Same reliability in the probe; used when tier 1 fails. |
| Reviewer, tier 3 | `qwen/qwen3.8-27b` (Groq) | A third family, used if both NVIDIA endpoints fail. |
| Injection screen | `meta-llama/llama-prompt-guard-2-86m` | Classifier, scores 0.998 on an injected issue and 0.0004 on a normal one in our probe. |

If every reviewer tier fails, the run stops with status `STOPPED` and the pull request is left without approval. A reviewer outage is never treated as approval. The tier that answered each call is logged in `state.json`.

## Alternatives considered
- **One model for every role.** Cheapest to operate and easiest to explain; it makes the reviewer share the implementer's blind spots. Kept as variant `same-model` in experiment E2.
- **Gemini as reviewer.** Attractive as a different vendor, but it answered none of our requests during the probe. Not used unless a later probe shows it answering.
- **Larger NVIDIA models for the builder too.** Would lift the 7k token cap. Deferred: NVIDIA's free-tier request limit was not measured, and a single working builder is easier to reason about. Revisit after the first runs.

## Consequences
- Availability, not capability, drove most choices; a different day may change the ranking. The probe script and results are in the repository so it can be repeated.
- Both Nemotron tiers share a vendor, so tier 2 is a weaker independence guarantee than tier 3.
- Models are free preview endpoints and may be withdrawn; the tier chain exists for that case.
- The weaker builder model is expected to fail some stages. That is acceptable as long as the failures are real and reported.

## Amendment (2026-11-16, after the first runs on GitHub)
Groq's free tier has a daily limit as well: 200,000 tokens per organisation and model (error text `tokens per day (TPD): Limit 200000`). One full run uses about 85,000 tokens and the local test runs before the first GitHub runs already used most of the quota of some keys, so the third run on issue #7 (Actions run 43923968438) stopped with "all tiers failed". The role table is therefore changed:

| Role | Tier 1 | Tier 2 |
|---|---|---|
| Planner | `gpt-oss-120b` (Groq) | `poolside/laguna-xs-2.1` (NVIDIA) |
| Implementer | `gpt-oss-120b` (Groq) | `poolside/laguna-xs-2.1` (NVIDIA) |
| Tester | `poolside/laguna-xs-2.1` (NVIDIA) | `gpt-oss-120b` (Groq) |
| Reviewer | `nemotron-3.5-super-vl-120b` | `nemotron-3-ultra-550b`, then `qwen3.8-27b` (Groq) |

The tester now uses a different model from the implementer, which supports the argument for a separate tester in ADR-001 (a different model is less likely to share the implementer's blind spots) and spends less of the Groq quota. A daily-quota error puts that key aside for at least 15 minutes and the role falls back to the other vendor. The reviewer is still a different vendor from every builder tier. The model that served each call is recorded in `state.json`, so results can be split by model.

## Second amendment (2026-11-17, after Actions runs 43938183218 and 43943135327)
New logging in the model client (`key#N of groq rate limited ...`) showed why runs on issue #7 took more than 50 minutes and stopped: all six Groq keys had used 195,000 to 199,000 of their 200,000 daily tokens (rolling 24 hours), so every Groq call waited for a quota that frees up only as the previous day's usage ages out. Our own earlier runs and local tests had spent it; one pipeline run costs about 85,000 tokens, so six keys allow about 14 runs per day, which is not enough for five issues, repeated attempts and two experiments.

Changes:

| Role | Tier 1 | Tier 2 |
|---|---|---|
| Planner | `poolside/laguna-xs-2.1` (NVIDIA) | `gpt-oss-120b` (Groq) |
| Implementer | `poolside/laguna-xs-2.1` (NVIDIA) | `gpt-oss-120b` (Groq) |
| Tester | `gpt-oss-120b` (Groq) | `nvidia/nemotron-3-ultra-550b-a55b` (NVIDIA) |
| Reviewer | unchanged | |

The tester still uses a different model from the implementer. When every key of a provider is set aside for more than 90 seconds, the client gives up on that tier at once instead of waiting (`test_a_tier_whose_keys_are_all_set_aside_is_skipped_at_once`). The tester's second tier, Nemotron Ultra, is also the reviewer's second tier; it is a different model from the implementer and from the reviewer's first tier, but the same vendor as the reviewer's first two tiers, which is noted as a threat to validity.

## Third amendment (2026-11-17, after Actions run 43953452086)
The second amendment made NVIDIA's `laguna-xs-2.1` the primary model for the planner and the implementer, with Groq as fallback. The next run (43953452086, issue #7) showed this was a poor choice: as planner, Laguna used all 25 calls of the stage budget without producing a specification and the stage stopped. It also hid a problem: with a fallback, a run can switch models half-way, and then a result can no longer be attributed to one model.

Decision, replacing both earlier role tables:

| Role | Model | If it is unavailable |
|---|---|---|
| Planner | `gpt-oss-120b` (Groq) | the stage stops and says why |
| Implementer | `gpt-oss-120b` (Groq) | the stage stops and says why |
| Tester | `poolside/laguna-xs-2.1` (NVIDIA) | the stage stops and says why |
| Reviewer | `nemotron-3.5-super`, then `nemotron-3-ultra`, then `qwen3.8-27b` | falls through the chain; if all fail, no approval |

Builder roles are pinned, so every recorded run has a known model. The reviewer keeps its chain because an unavailable reviewer must never block or approve silently, and the tier that answered is recorded. The cost is operational: a run started while the Groq daily quota (200,000 tokens per key and day, about 85,000 per pipeline run) is used up stops at once with that reason and is repeated later. Runs are therefore spaced out and every attempt, including the ones that stopped for this reason, is listed in `results/runs.md`.

## Fourth amendment (2026-11-17, after Actions runs 44138342662 and 44144840492)
The tester on NVIDIA's `poolside/laguna-xs-2.1` stopped stage 4 in both runs. In the first the stage was silent for more than 20 minutes: one request hung through all eight retries; with shorter timeouts (45 s, at most four) the second run ended stage 4 with `TimeoutError` after about five minutes. The same endpoint answered 6 of 6 simple tool-call requests from a runner (probe-models.yml, run 44146914224, 1 to 11 s) and most requests from a laptop, but in the pipeline individual calls took 20 to 28 s at prompts of about 3,000 tokens and some never answered. Measured from a laptop with 3,000 to 10,000-token prompts, Laguna's latency grew from about 4 s to 20 s and requests above 9,000 tokens timed out. `nemotron-3-ultra` answered 12 of 12 and 6 of 6 from the runner.

On Groq, 8 of 8 tool-call trials succeeded for each of `gpt-oss-20b`, `qwen3.8-27b` and `gpt-oss-120b` (0.5 to 1.8 s). The tester is now **`qwen/qwen3.8-27b` on Groq**: a different vendor and model family from the `gpt-oss-120b` implementer, which keeps the argument of ADR-001 for a tester that does not share the implementer's blind spots, and it has its own daily quota, which spares the `gpt-oss-120b` quota. The reviewer stays on NVIDIA (different vendor from every builder). Qwen is also the reviewer's third tier; that tier is only used if both NVIDIA models fail, and the tier that answered is recorded, so a review served by Qwen is visible in the data.

| Role | Model |
|---|---|
| Planner | `gpt-oss-120b` (Groq) |
| Implementer | `gpt-oss-120b` (Groq) |
| Tester | `qwen/qwen3.8-27b` (Groq) |
| Reviewer | `nemotron-3.5-super-vl-120b`, then `nemotron-3-ultra-550b`, then `qwen3.8-27b` |

## Fifth amendment (2026-11-17, after Actions runs 44152805967 and 44155499158)
Qwen as tester also failed in the pipeline. In run 44152805967 its `write_file` content was cut off after two tests and it repeated the identical call; with the new `write_file` feedback and a prompt for short tests, run 44155499158 still ended with only two of the six required tests after three attempts, the last one in a loop of repeated searches. A replay of stage 4 on recorded artifacts passed once with Qwen, so the behaviour is inconsistent.

On the same recorded artifacts, `openai/gpt-oss-20b` (Groq) produced a complete test file, one test per criterion, in 3 of 3 replays. It is the tester now. It is a smaller model of the same family as the implementer (`gpt-oss-120b`), so the tester differs from the implementer in size and context but not in vendor; the stronger separation (a different family) was tried twice and was less reliable than a model of the same family. It has its own daily token quota, which spares the `gpt-oss-120b` quota. The reviewer is a different vendor from every builder.

| Role | Model |
|---|---|
| Planner | `gpt-oss-120b` (Groq) |
| Implementer | `gpt-oss-120b` (Groq) |
| Tester | `gpt-oss-20b` (Groq) |
| Reviewer | `nemotron-3.5-super`, then `nemotron-3-ultra`, then `qwen3.8-27b` |

The replays also showed a defect in the specification written by the planner: it invented a `table=` parameter in an example, the tester faithfully tested it, and the implementation could not satisfy it. The planner prompt now forbids inventing API names or parameters, and a criterion that fails twice sends the run back to the requirements stage, not only to the design (ADR-002 amended).
