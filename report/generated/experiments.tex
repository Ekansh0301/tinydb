Both experiments use the frozen code (\code{autose-v1}, one crash fix in \code{v1.1}), the same five issues, the same hidden tests and the same gates (\code{experiment/variants.md}, \code{experiment/protocol.md}). Reruns after infrastructure faults are listed in \code{results/runs.md}; none of the results below comes from a run that stopped because of quota or an outage.

\textbf{E1, splitting the work (\adr{001}).} The design splits stages 1 to 4 between a planner, an implementer and a tester, each with its own inputs. The variant gives one agent (same model, \code{gpt-oss-120b}) the whole task in one conversation, with the same gates applied to what it produces and up to three attempts. Compared at the end of round 1 (Table~\ref{tab:e1}): the pipeline opened a pull request on issues \#4, \#6 and \#7 (hidden tests 4/4, 5/5 and 3/5, no regressions) and stopped at stage 4 (\#5) and stage 2 (\#8); the single agent produced \emph{no} pull request on any of the five issues. In 15 attempts it passed the gates for spec, design and implementation in five, but it never passed the test gate (no test named \code{test\_ac<N>}, which maps tests to criteria), and in eight attempts its answer lost the required format altogether (malformed tool calls, a repeated call, a request over the context limit). Token use is similar (102k to 218k per issue for the single agent, 120k to 228k for the pipeline), so the difference is not a matter of budget. Our reading: with a 7,000-token window one conversation cannot hold requirements, design, code and tests, and nothing tells it which part failed; the pipeline gives each stage a small context and an explicit gate and back-edge. This does not show that splitting beats one agent for strong models, and the single agent has no stage-level feedback, so the experiment tests splitting together with gating. The result supports \adr{001}; we did not change the design because of it.

\textbf{E2, reviewer independence (\adr{008}).} The final reviewer was run three times on each of the five seeded pull requests, once per variant (Table~\ref{tab:e2}). The independent reviewer (Nemotron, own job, issue plus diff plus repository only) approved all six reviews of the correct pull requests and caught the defect in eight of its nine reviews of the wrong ones; the ninth gave no valid verdict and counts as no review. It found the bugs by running snippets of its own (on pull request \#16 it showed that \code{startswith('al')} returned the results of an earlier \code{startswith('Al')}). The same-model reviewer (the builder's \code{gpt-oss-120b}, fresh context, same prompt and permissions) approved eight of nine wrong pull requests: it ran the test suite once, read the pull request's own tests, and approved them, using about 3,400 tokens against 54,000. Our evidence rule did not stop this, because it checks that evidence exists, not that it could have found a defect. The result supports \adr{008} (the choice of a different model and of a verification habit matter, not the separate job alone).

\textbf{E2b, a larger reviewer (bonus).} Because the independent reviewer's first tier has 12\,B active parameters while the builder has about 5\,B, we asked whether the result depends on the reviewer being large. We reran the same 15 reviews with the 550\,B Nemotron (55\,B active) as first tier. It produced 15 valid reviews, caught all nine wrong pull requests and approved all six correct ones, for about twice the tokens (105,000 per review). Both reviewers are far better than the same-model one; the larger one is more reliable (no invalid review). We therefore changed the design \emph{after} the recorded runs: the reviewer chain now starts with the larger model (\adr{008} amendment, \code{autose-v1.2}). The recorded pipeline reviews were made by the smaller first tier, as frozen.
